# 新写技术方案输入示例

> **版本**: v1.0.0
> **用途**: 用于从主题和少量背景开始，共创技术方案、设计文档或 RFC
> **边界**: 本文档不负责工作流路由；工作流应由目标 Skill 根据“目的”和“提供的信息”判断

## 适用场景

- 用户有明确主题或目标，但还没有完整文档。
- 目标产物是 `design.md`、`rfc.md` 或同类技术方案。
- 重点是先建立写作契约，再逐步补齐范围、约束、风险和验收。

## 建议提供的信息

- 必需: 主题、目标读者、读完后希望对方做出的决定或行动。
- 必需: 已知背景、现状痛点、关键约束、必须保留或必须避开的范围。
- 可选: 备选方案、已有讨论结论、上线时间、Owner、验收标准、相关文档路径。

## 可直接复制输入模板

```markdown
使用 `kz-doc-coauthoring`，帮我共创一份 `{技术方案/RFC/设计文档}`。

主题：{要解决的问题或方案名称}
目标读者：{谁会读，他们关心什么}
预期影响：{读完后希望他们做什么决定或采取什么行动}
已知背景：{当前现状、痛点、已有结论}
约束：{时间线、兼容性、必须包含或不能包含的内容}
目标文件：{DOC_PATH，如 design.md}

请先输出写作契约，再给出目录骨架和每章要回答的问题。
```

## 真实输入示例（可选）

```markdown
使用 `kz-doc-coauthoring`，帮我共创一份设计文档。

主题：把现有手工工资导入流程改为可校验、可回滚的批量导入能力。
目标读者：后端、前端、财务运营和项目负责人。
预期影响：让大家确认导入范围、错误反馈、回滚策略和上线验收。
已知背景：现在主要靠人工检查 Excel，错误发生后排查慢。
约束：不改变现有财务系统字段，第一版只覆盖月度工资表。
目标文件：design.md

请先输出写作契约，再给出目录骨架和每章要回答的问题。
```

## 路由判断（可选）

该输入通常先进入 `step-meta-context`；若用户已经一次性提供了大量材料，可跳到 `step-context-gathering`。
