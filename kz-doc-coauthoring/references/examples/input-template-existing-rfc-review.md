# 已有文档审校输入示例

> **版本**: v1.0.0
> **用途**: 用于对已有 RFC、设计文档、README 或 runbook 做读者测试与最终审校
> **边界**: 本文档不负责工作流路由；工作流应由目标 Skill 根据“目的”和“提供的信息”判断

## 适用场景

- 用户已经有一份文档，希望发现歧义、缺口、冲突或不可执行结论。
- 目标产物是审校清单、读者问题清单、修补建议，而不是从零重写全文。
- 重点是独立读取文档内容，避免依赖之前的对话上下文。

## 建议提供的信息

- 必需: 待审校文档路径或正文片段。
- 必需: 目标读者和读完后应采取的行动或决策。
- 可选: 需要重点检查的方面，例如术语一致性、风险、Owner、验收方式、可执行性。

## 可直接复制输入模板

```markdown
使用 `kz-doc-coauthoring`，从读者视角审校 `{DOC_PATH}`。

目标读者：{谁会读}
预期影响：{读完后他们应该做什么决定或采取什么行动}
重点检查：{歧义/缺失信息/自相矛盾/术语一致/下一步可执行性}

请先给出 5-10 个真实读者会问的问题，再列出需要修补的章节和建议改法。
```

## 真实输入示例（可选）

```markdown
使用 `kz-doc-coauthoring`，从读者视角审校 docs/rfc/import-validation.md。

目标读者：后端、前端、财务运营和项目负责人。
预期影响：读完后能确认第一版导入校验范围和上线验收方式。
重点检查：歧义、缺失信息、自相矛盾、术语一致、下一步可执行性。

请先给出 5-10 个真实读者会问的问题，再列出需要修补的章节和建议改法。
```

## 路由判断（可选）

该输入通常进入 `step-reader-testing`；如果用户强调“发出前检查”“交付清单”“术语一致”，优先进入 `step-final-review`。
