# 产出类型打法

> **版本**: v1.0.6
> **用途**: 根据用户要的媒介选择不同的设计骨架和验证重点

## 原型 / App mockup

- 先问或判断交付形态：overview 平铺还是 flow demo。
- overview 适合设计走查：多屏并排、每屏完整、状态清楚。
- flow demo 适合演示路径：单台设备、状态管理、tab/button/modal 都能点。
- 内容型 App 优先使用真实图片；装饰性头图如果和内容无关，宁可不用。
- 交付前至少点击 3 个关键动作：进入详情、tab 切换、主要 CTA。

## HTML Demo / 工具界面

- 首屏就是可用体验，不做营销式 landing，除非用户明确要 landing page。
- 操作型工具界面要安静、紧凑、易扫描，不用大 hero、装饰卡片和空泛文案。
- 工具界面使用 utility copy：标题和说明优先表达范围、状态、数据新鲜度、动作和决策价值，不写广告式口号。
- 控件选择符合习惯：按钮用于命令，segmented control 用于模式，slider/stepper/input 用于数值，tabs 用于视图。
- 使用图标按钮时优先用已有图标库；陌生图标补 tooltip。
- 保留 1 个可被记住的视觉签名，例如特殊排版、非对称构图、关键转场或真实素材处理；不要同时堆多个炫技点。

## Landing / 品牌页

- 只有用户明确要 landing、品牌页、产品介绍、场馆/作品集页面或发布页时才使用本打法；工具界面不要自动套 hero。
- 首屏必须让品牌、产品或对象名成为明确第一信号；隐藏导航后仍应知道这是什么。
- 首屏需要一个真实视觉锚点：产品图、场景图、界面截图、实物影像或强叙事画面；装饰纹理不算主视觉。
- Hero 只保留一个构图和一个主动作；默认不要 hero card、统计条、logo 云、标签堆或浮动 dashboard。
- 文字列要窄，放在图像的稳定明暗区域；文字对比和移动端点击目标必须可靠。
- 每个 section 只做一件事：解释、证明、深化或转化；若两个 section 只是在重复同一种情绪，删掉或合并。
- 如果存在固定 header，首屏高度要把 header 算进去；使用 `100vh/100svh` 时避免首屏内容被挤出或遮挡。

## 幻灯片 / Deck

- 固定 16:9 或用户指定尺寸，先定每页核心句。
- 不把网页 section 搬进 slide；slide 是演讲节奏，不是长页面。
- 多页 deck 先给每页指定唯一页面角色：封面、目录、章节分隔、内容页、收束页；不要让每页都长成同一种内容卡片。
- 内容页子类型按信息任务选择：文字观点、图文混排、数据可视化、并排对比、时间线/流程、图片展示。
- 封面负责定调，目录负责预期，章节分隔负责转场，内容页负责推进一个论点，收束页负责总结或行动。
- 同一章节内保持版式家族一致，但相邻页面要有节奏变化：列布局、图文比例、数字 callout、对比框或时间轴择一使用。
- 页内层级控制在标题、主体、注释三层以内。
- 若要导出 PDF/PPTX，构建时就考虑文字矢量、字体可用性和页面边界。

## 信息图 / 可视化

- 先确认数据是否真实、单位是否明确、比较关系是否成立。
- 图表优先服务问题，不为炫技选复杂图。
- 先写清用户要回答的问题，再按数据关系选图表类型：趋势用 line/area，类别对比用 bar/column，构成占比用 pie/treemap，相关关系用 scatter/network，流向用 sankey/flow，分布用 histogram/boxplot，层级关系用 treemap/org/mind map。
- 当数据字段、聚合、单位或时间粒度不清楚时，先补 `Visualization Spec`；不要直接画一张看起来合理的图。
- 标签、注释和来源要可读；不要把图例藏到用户读不出来的位置。
- 颜色数量服务分类、状态或强调，不用多色填满画面；同一语义在多个图表里保持同一颜色。
- 若类别、系列或节点过多，先过滤 Top-N、聚合长尾或改成表格/小 multiples；不要用密集图表制造信息量。
- 避免误导性比例：截断坐标轴、双轴、百分比堆叠、面积编码和 3D 效果必须有明确理由。
- 交接给实现系统时，输出 `Visualization Spec`，包括 question、chart type、data fields、encoding、aggregation、unit、time grain、labels/legend、source、interaction、empty/error state。

## 动画 / 视频

- 先定时长、用途、比例、关键帧、镜头节奏和是否需要音频。
- 时间轴要有开端、发展、焦点和收束；不要每段独立淡入淡出。
- 动画中的文字要按实际观看时长可读，不把 slide 级长文塞进镜头。
- 导出前检查首帧、末帧、循环、进度条污染、音轨存在和文件大小。

## 设计方向探索

- 推荐 3 个方向，每个方向必须来自不同视觉逻辑；必要时从 [风格 Profiles](style-profiles.md) 选择 2-3 个 profile 作为起点。
- 每个方向说明适合原因、标志性视觉特征、适用风险和最小 demo 形态。
- 每个方向都写一句 aesthetic thesis，说明它的语气、主记忆点和复杂度边界。
- profile 不是模板；用户选中后要结合真实资产、媒介和内容重新收敛成一个具体设计系统。
- 用户选中后，再进入主流程做完整产物；不要把方向建议当成最终交付。

## UI 规范 / 实现交接

- 先判断是否已有可用设计；没有时先回到 brief、资产和方向步骤，不凭空写组件规范。
- 默认输出 `design-brief.md`、`ui-spec.md`、`implementation-handoff.md`，必要时附 HTML、截图或导出图作为视觉参考。
- `ui-spec.md` 写通用设计决策：信息架构、状态、交互、tokens、组件意图、响应式和素材缺口。
- `implementation-handoff.md` 写目标系统适配：组件映射、token 映射、布局映射、禁用项、开放问题和验收命令。
- 若目标实现系统有自己的组件规范，先读取它；不要把 HTML/CSS 里的自由样式直接要求实现方照搬。
- 若目标系统未知，只交付系统无关规范，并列出实现系统需要补充的组件库、theme/token、布局系统、禁止方式和验证命令。

## 设计评审

默认从 7 个维度审查：

| 维度 | 看什么 |
|---|---|
| 目标适配 | 是否服务受众和场景 |
| 信息层级 | 用户第一眼能否抓住主信息 |
| 品牌识别 | 是否像该品牌，而不是通用模板 |
| 媒介适配 | 是否像正确媒介的产物 |
| 细节执行 | 间距、对齐、文字、状态、图像质量 |
| 可用性 | 是否能读、能点、能演示 |
| 原创性 | 是否摆脱 AI 默认套路 |

输出时按严重度给修复动作：致命、重要、优化。
