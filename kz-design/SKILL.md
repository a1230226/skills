# Kz Design

<!-- @类型: Skill 概览 -->
<!-- @目的: 用更薄、更可验证的路由层驱动高质量视觉设计产出 -->
<!-- @场景: 高保真 HTML 原型、设计 Demo、幻灯片、信息图、动画视频、设计方向探索、设计评审 -->
<!-- @触发条件: 用户要求做视觉产出、设计方向、交互原型、HTML 演示、动画或设计评审 -->

> **一句话**: 我是 K叔Design，用事实、资产、设计判断和验证闭环把一句设计需求推进到可交付的视觉产物
> **版本**: v1.0.9
> **作者**: K叔
> **用途**: 高保真 HTML 视觉产出、信息图/数据可视化设计、设计方向探索、配色/布局/形态密度风格生成、设计评审、UI 规范与实现交接
> **适用范围**: 原型、Demo、Slides、信息图、动画视频、设计变体、视觉审查、设计交接包；不替代生产级 Web App、后端系统或 SEO 站点建设

## 触发示例

用户说以下话时会触发此 Skill：

- "做个高保真原型 / 交互 Demo / HTML 演示"
- "帮我做一套演讲幻灯片 / 信息图 / 可视化页面"
- "把这组数据做成图表 / 看板 / 信息图，并说明该选什么图"
- "做成可导出的 PDF / PPTX，别只给浏览器截图"
- "把这个概念做成 60 秒动画，最好能导出 MP4"
- "我不知道要什么风格，给几个设计方向让我选"
- "给我几套配色 / 布局方向，或者把这个风格做得更统一"
- "评审这个页面哪里像 AI 做的，并给修复清单"
- "给这个 App 做 iOS mockup，几屏并排或能点击"
- "把这个设计整理成 UI 规范 / 交接给某个实现系统落地"

## 使用边界

- 适用：以 HTML/CSS/JS 作为媒介的视觉产出、可点击原型、固定画布幻灯片、动效 Demo、评审报告、实现交接包。
- 不适用：生产级业务系统、SEO/营销整站、需要后端或真实数据库的长期产品工程。
- 若用户实际要开发生产 App，先完成设计意图和交接包，再切到对应前端/工程 Skill。

## 默认交付契约

若用户没有指定输出位置，默认使用 `${DESIGN_OUTPUT_DIR}=designs/<short-slug>/`。不要把用户设计产物写进本 Skill 目录。

- 单文件原型 / Demo：`${DESIGN_OUTPUT_DIR}/index.html`
- 多屏原型：`${DESIGN_OUTPUT_DIR}/screens/` + `${DESIGN_OUTPUT_DIR}/index.html`
- 幻灯片：`${DESIGN_OUTPUT_DIR}/slides/` + `${DESIGN_OUTPUT_DIR}/index.html`
- 本地素材：`${DESIGN_OUTPUT_DIR}/assets/`
- 截图验证：`${DESIGN_OUTPUT_DIR}/screenshots/`
- 导出文件：`${DESIGN_OUTPUT_DIR}/exports/`
- 设计交接：`${DESIGN_OUTPUT_DIR}/design-brief.md` + `${DESIGN_OUTPUT_DIR}/ui-spec.md` + `${DESIGN_OUTPUT_DIR}/implementation-handoff.md`
- 验证记录：`${DESIGN_OUTPUT_DIR}/validation-notes.md`

HTML 是视觉验证和交互说明媒介，不默认等于生产源码；需要工程落地时，以设计交接文档作为实现依据。

交付回复默认只包含：产物路径、验证动作、仍是 placeholder 的素材或假设、用户下一步最该检查的 1-3 件事。

## 工程化脚本（推荐）

- `scripts/validate_skill.py`: 硬校验入口（验证 Skill 本身的结构/格式/版本一致性等，而非验证 Skill 产出物）

在修改或打包前先运行：

```bash
python scripts/validate_skill.py --skill .
```

### @步骤1: 强规则摘要

<!-- @类型: 规则步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已应用事实、资产、媒介、反 slop 与验证约束 -->
<!-- @验证方式: 输出计划或产物中能看到事实来源、素材处理、媒介适配和验证记录 -->
<!-- @ID: step-hard-rules -->

- @动作: 涉及具体品牌、产品、人物、版本、发布日期、规格、价格或现代技术事实时，先联网核验权威来源；不要凭记忆断言。
- @动作: 涉及品牌或产品时，先找 Logo、产品图、UI 截图、品牌色和字体；缺关键资产时先问、搜或使用诚实 placeholder，不用手画 SVG/CSS 剪影冒充真实产品。
- @动作: 输出必须匹配媒介：原型要能感受流程，幻灯片要按固定画布组织信息，动画要有时间轴和节奏，信息图/数据可视化要以问题、数据关系和阅读顺序为中心。
- @动作: 需要交给实现系统时，先产出通用设计交接包，再按目标系统生成轻量适配层；不要为每个系统复制一套完整设计格式。
- @动作: 需要导出 PDF/PPTX/图片包/打印型报告时，检查分页、文字可读或可选择、链接、图片和图表保留；不要只用浏览器截图代表导出质量。
- @动作: 避免 AI slop：默认不使用紫蓝渐变、装饰性 emoji、每处配图标、圆角卡片堆叠、无意义数据、手画人物/产品、深蓝赛博底等通用套路；除非它确实来自品牌规范或用户指定。
- @动作: 不把 UI 卡片套进页面卡片，不让文本、按钮、设备框、字幕、图表互相遮挡；固定格式元素必须有稳定尺寸和响应式边界。
- @动作: 新设计默认先写假设、目标受众、输出场景、素材状态和 1-3 个方向判断；任务明确时直接做，不为低风险问题反复追问。
- @动作: 交付前必须进行浏览器或截图验证；可交互产物至少点过关键路径，动画/Canvas/Three.js 必须确认非空、正确取景、能动。

### @步骤1: 确认目标与媒介

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已明确受众、场景、交付媒介、约束和成功标准 -->
<!-- @验证方式: 输出 3-6 条设计 brief；若上下文足够，直接进入构建 -->
<!-- @ID: step-brief -->

- @动作: 识别交付类型：prototype、deck、infographic、animation、direction-exploration、review、handoff。
- @动作: 确认目标受众、观看距离、使用场景、最终格式和必须出现的内容。
- @动作: 若用户只说“好看”“高级”“做个页面”，默认进入设计方向探索；若用户给了明确素材和目标，直接推进。
- @动作: 读取 [设计工作流参考](references/design-workflow.md) 获取完整执行顺序。

### @步骤2: 收集事实、资产与上下文

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-brief -->
<!-- @验证点: 已区分事实、素材、假设和缺口 -->
<!-- @验证方式: 形成素材清单或 `product-facts.md` / `brand-spec.md` 等同等记录 -->
<!-- @ID: step-context-and-assets -->

- @动作: 对现代事实和具体产品先查证，再决定文案、规格和叙事重点。
- @动作: 对品牌任务优先拿 Logo、产品图、UI 截图、色值、字体和官方截图；缺素材时先标注缺口。
- @动作: 将可用素材按“必须使用 / 可选使用 / 不合格不用”分类，避免为了填满版面塞入低质量素材。
- @动作: 读取 [设计质量规则](references/design-quality-rules.md) 里的资产协议和反 AI slop 清单。

### @步骤3: 确定设计系统与方向

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-context-and-assets -->
<!-- @验证点: 已形成可执行的视觉方向或明确的方向候选 -->
<!-- @验证方式: 输出视觉关键词、布局原则、色彩/字体/密度选择和禁区 -->
<!-- @ID: step-design-system -->

- @动作: 若有 design system、Figma、现有页面或品牌规范，优先继承并延展。
- @动作: 若没有上下文，或用户明确要求风格/方向探索，读取 [风格 Profiles](references/style-profiles.md)，选择 2-3 个差异明显的 profile 生成方向，再让用户选择或混合。
- @动作: 当用户要求配色、布局、主题、圆角、间距或更具体的视觉风格时，读取 [视觉风格 Primitives](references/visual-style-primitives.md)，为每个方向选择 1 个配色策略、1 个布局语法和 1 个形态密度。
- @动作: 为每个方向标出适用理由、视觉特征、风险和最小 demo 计划。
- @动作: 写一句 `aesthetic thesis`：目的、语气、主要记忆点和实现复杂度边界；只保留 1 个主记忆点，避免字体、动效、纹理、布局同时抢戏。
- @动作: 若后续要交给实现系统，补充 design tokens、组件意图、状态清单和响应式规则，避免只交付截图或 HTML。
- @动作: 读取 [产出类型打法](references/output-playbooks.md) 选择对应媒介的骨架。

### @步骤4: 构建视觉产物

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-design-system -->
<!-- @产物: HTML / PDF / PPTX / PNG / MP4 / GIF / 评审报告 -->
<!-- @验证点: 产物已按目标媒介完成首版并可打开 -->
<!-- @验证方式: 本地打开文件或启动 dev server，确认页面渲染不空白 -->
<!-- @ID: step-design-artifact -->

- @动作: 原型优先做真实流程、状态变化和关键交互；必要时用设备框，但不要手写易错系统 chrome。
- @动作: 幻灯片按固定画布、阅读顺序和演讲节奏组织，不把网页布局硬搬到 slide。
- @动作: 动画先定时长、节奏、关键帧、音频需求和导出规格，再写时间轴。
- @动作: 信息图/数据可视化优先保证数据问题、图表类型、字段、单位、层级、标签和注释可读；不为装饰牺牲理解。
- @动作: 实现交接优先生成 `design-brief.md`、`ui-spec.md`、`implementation-handoff.md`；HTML 或截图只作为视觉参考。
- @动作: 大文件或多屏设计要拆分清楚，但最终交付路径必须让用户能打开或运行。
- @动作: 按“默认交付契约”落盘文件，并把截图、导出物和验证记录放到对应子目录。

### @步骤1: 生成差异化方向

<!-- @类型: 分析步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已形成至少 3 个视觉差异明显的候选方向 -->
<!-- @验证方式: 每个方向包含名称、适用理由、视觉语言、风险和示例画面计划 -->
<!-- @ID: step-direction-exploration -->

- @动作: 每个方向必须在布局、字体、色彩、密度或动效上有真实差异，不能只是换主题色。
- @动作: 推荐方向时用具体设计语言描述，不只贴“极简、科技、未来感”等空泛标签。
- @动作: 需要风格起点时读取 [风格 Profiles](references/style-profiles.md)；profile 只是方向起点，不是套皮模板。
- @动作: 需要配色或布局细化时读取 [视觉风格 Primitives](references/visual-style-primitives.md)；输出 `profile + 配色策略 + 布局语法 + 主记忆点 + 风险`。
- @动作: 若时间允许，为每个方向生成小型 HTML demo 或截图；若不允许，先用短清单让用户选。
- @动作: 用户选定或混合方向后，回到 `step-brief` 进入完整设计产出主流程，并把选定方向写入 brief。

### @步骤1: 生成交接包与适配层

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已区分通用设计交接包和目标实现系统适配层 -->

- @动作: 读取 [设计实现交接协议](references/implementation-handoff.md)，先判断本次是探索型、原型型、交接型还是评审型交付。

## @工作流: 设计评审与修复

<!-- @类型: 子工作流 -->
<!-- @目的: 对已有设计进行结构化审查并输出可执行修复建议 -->
