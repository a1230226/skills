> **一句话**: 我负责把一个仓库整理成“AI 可以稳定接手”的初始状态。
> **版本**: v1.11.1
> **用途**: 项目初始化、AGENTS.md 生成、Git/BMAD 拓扑发现、项目画像沉淀
> **适用范围**: 单仓、monorepo、单子仓库容器、嵌套多仓库项目

## Overview

本 Skill 不是单纯生成 `AGENTS.md`，而是先建立**项目事实**，再基于这些事实产出初始化工件。默认先扫描 Git 仓库、BMAD 工件、代码根目录、文档目录和常见构建入口，再生成：

- `AGENTS.md`

在以下场景，建议同步生成或补齐 `project-context.md`：

- 项目存在多仓库、模板系统、工作流抽象或 BMAD 工件
- 仓库不仅要“能执行”，还需要“能快速理解”
- 用户明确要求建立项目画像、项目背景说明或上下文基线

详细发现规则见 [repo-discovery.md](references/repo-discovery.md)，输出口径见 [output-contract.md](references/output-contract.md)。如需确定性扫描，使用 `python scripts/scan_repo.py --root <path>`。
任务收尾时不要只说“已完成”，必须按 [output-contract.md](references/output-contract.md) 说明本轮完成度、主线目标状态、验证证明和剩余问题性质。

如果项目已经存在 `AGENTS.md` 或 `project-context.md`，本 Skill 默认优先做“事实校正 + 缺口补齐”，而不是机械重写；只有当现有文档和仓库事实明显冲突、或用户明确要求重构时，才整体重写。

本 Skill 支持显式指定输出语言，建议使用 `${OUTPUT_LANGUAGE}` 变量承载，常见值包括 `中文`、`English`。如果用户未指定，默认跟随用户当前对话语言；若无法判断，则默认使用 `中文`。

若项目包含 Python 技术栈，初始化时还要把“Python 执行环境”识别为项目事实的一部分，而不是默认使用系统 `python`。优先检查 `${TARGET_ROOT}` 下是否存在 `.conda.env`，再结合 `environment.yml`、`conda.yml`、`pyproject.toml`、`requirements.txt`、`poetry.lock`、`uv.lock` 等信号推断推荐环境；但由于开发环境自动识别可能出错，即便识别出 conda 环境名或 Python 版本，也必须先与用户确认后，才能写入 `AGENTS.md` 或作为后续执行前提。

初始化时不要只把仓库当成“目录树”，还要把它识别成一个可能已经部分成型的“仓库级操作系统”。
重点检查这些入口是否存在并已形成协作约束：`AGENTS.md`、`README*`、`docs/contributing.md`、`justfile` / `Makefile` / `Taskfile`、`.github/workflows/*.yml`、schema / fixture / snapshot 目录、issue / PR 模板。

若扫描结果显示项目已接入 BMAD，则不要只停留在目录级发现；应进一步把 `_bmad-output/` 下可读文档视为强化项目认知的高价值入口。优先读取其中能解释项目目标、阶段状态、方案设计、故事拆分或任务上下文的文档，用于提升 `AGENTS.md` 与 `project-context.md` 的事实质量。

### @步骤1: 确定初始化范围

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @验证点: 已确认本轮初始化的根目录与作用范围 -->
<!-- @验证方式: 能说清“目标目录是什么、是整仓库还是某个子模块” -->
<!-- @ID: step-scope-target -->

- @动作: 确定目标根目录；若用户未显式指定，则默认使用当前工作目录作为 `${TARGET_ROOT}`
- @动作: 判断本轮初始化范围是“整个项目”还是“某个子模块/子仓库”
- @动作: 确定输出语言 `${OUTPUT_LANGUAGE}`；支持至少 `中文` 与 `English`
- @动作: 若当前目录下存在多个 Git 仓库候选，明确是否以 `${TARGET_ROOT}` 为项目容器、还是以某个子仓库为主初始化对象

@提示: 遇到多仓库项目时，不要默认根目录就是实际代码仓库；先把“项目容器”与“代码主仓库”区分开。输出语言一旦确定，初始化文档应保持一致，不要中英混写。

### @步骤2: 扫描项目事实

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-scope-target -->
<!-- @验证点: 已采集 Git/BMAD/代码/文档/构建入口的结构事实 -->
<!-- @验证方式: 能列出仓库拓扑、主要代码目录、现有初始化文档与构建清单 -->
<!-- @ID: step-scan-facts -->

- @动作: 运行 `python scripts/scan_repo.py --root "${TARGET_ROOT}"` 获取结构化扫描结果
- @动作: 按需补充人工判断，识别“主代码仓库”“嵌套子仓库”“仅承载 BMAD 工件的目录”
- @动作: 记录现有 `AGENTS.md`、`project-context.md`、`README*`、架构文档和常见 manifest
- @动作: 若项目疑似包含 Python 技术栈，额外检查 `${TARGET_ROOT}/.conda.env` 是否存在，并记录其中约定的 conda 环境名或环境配置线索
- @动作: 同步提取 Python 环境信号：`environment.yml`、`conda.yml`、`pyproject.toml`、`requirements.txt`、`poetry.lock`、`uv.lock`、`runtime.txt`
- @动作: 做 discovery-first 事实采集，优先识别统一命令入口、CI workflow、snapshot / fixture / schema 生成链路、贡献文档和 issue 模板
- @动作: 提炼构建与验证入口，如 `pytest`、`npm test`、`poetry run`、`make`、`cargo test` 等
- @动作: 若识别到 `_bmad/` 或 `_bmad-output/`，继续检索 `_bmad-output/` 下可读文档，优先读取能解释项目目标、阶段状态、路线图、story、设计决策的文件
- @动作: 使用扫描结果中的 `reading_priority` 作为初始化阶段的默认阅读顺序，优先阅读 `AGENTS.md`、`project-context.md`、根 `README*` 与 `_bmad-output/` 高价值候选文档
- @动作: 把 BMAD 文档中对项目理解有增益的结论回写为“辅助事实”，但不要覆盖代码和仓库结构已经证明的硬事实

@提示: 扫描结果是事实输入，不等于最终结论。对“哪个仓库是主仓库、哪个目录是代码主目录”仍需要结合上下文做判断。扫描脚本应忽略缓存目录与依赖目录，避免把噪声文档误识别成项目事实。Python / conda 环境自动识别也只是一阶推断，不能跳过用户确认。BMAD 文档可以强化认知，但不应替代代码与仓库结构本身的证据优先级。

### @步骤3: 确认 Python 环境事实

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-scan-facts -->
<!-- @验证点: 已明确 Python 项目是否存在推荐执行环境，且自动识别结果已与用户确认 -->
<!-- @验证方式: 能说明 `.conda.env` 是否存在、当前推断的 conda 环境是什么、哪些信息已被用户确认 -->
<!-- @ID: step-confirm-python-env -->

- @动作: 若仓库不存在 Python 技术栈信号，可跳过本步骤后续细化动作，并明确“当前项目未识别到 Python 运行时约束”
- @动作: 若存在 `.conda.env`，将其视为高优先级信号，用于推断推荐的 conda 环境名或初始化命令
- @动作: 若不存在 `.conda.env`，再结合 `environment.yml`、`conda.yml`、`pyproject.toml`、`poetry.lock`、`uv.lock` 与 README 中的环境说明做自动识别
- @动作: 即便已识别出推荐 conda 环境，也必须向用户确认；不要把自动识别结果直接写成硬规范
- @动作: 若自动识别结果存在冲突、缺失或置信度不高，主动询问用户当前开发环境使用的 Python / conda 方案，再继续生成初始化文档
- @动作: 只有在用户明确确认后，才把 Python 版本、conda 环境名、激活方式和运行入口写入 `AGENTS.md` 或相关初始化工件

@提示: 这里的目标不是“替用户决定环境”，而是把“项目实际执行环境”沉淀成后续 skill 可稳定复用的事实。自动识别负责缩小范围，最终口径仍以用户确认结果为准。

### @步骤4: 判定项目拓扑与职责边界

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-confirm-python-env -->
<!-- @验证点: 已完成项目分类，并为关键目录写出职责边界 -->
<!-- @验证方式: 能明确区分单仓 / monorepo / 嵌套多仓库，并列出每类关键目录职责 -->
<!-- @ID: step-classify-topology -->

- @动作: 将项目分类为：`single-repo`、`monorepo`、`single-subrepo`、`nested-multi-repo`、`no-git`
- @动作: 明确哪些目录属于：项目容器、主代码仓库、子模块仓库、BMAD 工件目录、文档目录、测试目录
- @动作: 明确仓库里哪些文件在承担“规则入口”“命令入口”“门禁入口”“契约验证入口”的职责
- @动作: 标记共享热点：路由入口、数据库配置、模型目录、部署配置、统一脚本入口
- @动作: 如果不同目录的 Git 归属不同，准备把这部分直接写入 `AGENTS.md`

@提示: 当前项目最容易踩坑的不是“文件在哪”，而是“哪个文件属于哪个仓库、应该在哪个目录执行 Git”。

### @步骤5: 提炼项目画像

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-classify-topology -->
<!-- @验证点: 已把结构化事实压缩为可被后续 agent 复用的项目理解框架 -->
<!-- @验证方式: 能给出项目一句话定位、当前阶段判断、关键层次结构和常见误判提醒 -->
<!-- @ID: step-summarize-project-context -->

- @动作: 基于扫描结果、`reading_priority` 推荐顺序、README、关键代码目录与 BMAD 文档，提炼“项目一句话画像”
- @动作: 判断项目当前阶段，例如练手项目、平台化演进中、稳定业务系统、模板/工具型仓库等
- @动作: 总结 3-5 个最重要的结构层次，例如业务应用层、工作流层、复用能力层、协作交付层
- @动作: 提炼最容易误判的事实，例如多仓库归属、运行时类型、模板目录职责、BMAD 工件作用
- @动作: 若项目复杂度较高或用户明确要求，准备把这些内容沉淀到 `project-context.md`

@提示: 这一步的目标不是写介绍文案，而是把“后续 agent 为什么容易看不懂这个项目”提前消解掉。

### @步骤6: 规划初始化产物

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-summarize-project-context -->
<!-- @验证点: 已明确本轮要生成哪些文档，以及各自承载什么信息 -->
<!-- @验证方式: 能列出目标文件与每个文件的职责 -->
<!-- @ID: step-plan-outputs -->

- @动作: 按 [output-contract.md](references/output-contract.md) 规划初始化产物
- @动作: 默认至少生成：
  - `AGENTS.md`
- @动作: 把 `AGENTS.md` 视为唯一主入口；Git 根路由、默认工作目录、分支与收尾约定、多仓库暂停点统一收敛在 `AGENTS.md`
- @动作: 把“任务收尾说明”也视为 `AGENTS.md` 的正式组成部分，而不是只留在 agent 临时输出里；至少规划 `本轮完成度`、`主线目标是否完成`、`已完成的关键改动`、`已执行的验证`、`未完成 / 阻塞项`、`下一刀建议`
- @动作: 规划每份产物的语言策略：标题、正文、待确认事项、术语注释统一跟随 `${OUTPUT_LANGUAGE}`，文件名保持项目既有约定
- @动作: 如果项目已经有其中某些文件，决定是“重写”“增量补全”还是“只修正缺失章节”
- @动作: 若用户已确认 Python / conda 环境信息，则把 `.conda.env`、推荐 conda 环境名、激活命令、测试/运行命令对应的执行环境纳入输出规划
- @动作: 若 Python 环境尚未被用户确认，不要把自动识别结果写成确定事实；只能在文档里标为“待确认事项”
- @动作: 遵循默认更新策略：
  - 现有文档结构基本可用且事实大体正确时，优先增量补齐
  - 现有文档缺少 Git 根路由、目录职责、运行/测试入口时，按缺项补章节
  - 现有文档把错误 Git 根、错误主仓库或错误收尾规则写成硬规范时，优先重写相关章节
- @动作: 如果现有文档语言与 `${OUTPUT_LANGUAGE}` 不一致，先判断是保留既有语言、做双语迁移，还是整份转写到目标语言
- @动作: 当项目满足以下任一条件时，建议同步生成 `project-context.md`：存在多仓库、存在 `source/workflows` / `templates` 一类抽象层、存在 `_bmad-output/`、用户明确要求建立项目画像
- @动作: 只有在项目足够简单且用户只要求执行规则时，才可以只产出 `AGENTS.md`

### @步骤7: 生成文档草稿

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-plan-outputs -->
<!-- @验证点: 输出文档内容与扫描事实一致，且覆盖核心协作规则 -->
<!-- @验证方式: 逐项检查文档是否覆盖拓扑、Git、运行/测试入口、目录职责与风险提示 -->
<!-- @ID: step-generate-docs -->

- @动作: 使用 `assets/AGENTS.template.md` 作为结构参考，生成或更新 `AGENTS.md`
- @动作: 根据 `${OUTPUT_LANGUAGE}` 选择中文或英文表述；保留代码、路径、命令、分支名等技术字面量原样
- @动作: 把“统一本地入口”“CI 门禁”“契约工件”“可比较的 UI / 输出证据”写成后续开发能直接消费的规则
- @动作: 把复杂目录结构与拓扑路由也直接收敛进 `AGENTS.md`，至少覆盖：项目容器目录、主代码仓库、其他独立仓库、BMAD 工件目录、文档目录，以及 Git 根路由、默认 Git 工作目录、主分支推断、分支与收尾约定、多仓库暂停点、本地入口与门禁映射
- @动作: 把任务收尾口径直接写入 `AGENTS.md`，作为项目级交付规范；不要只在本次回复里临时说一次
- @动作: 对 Python 项目，把“推荐 conda 环境 / `.conda.env` / 激活方式 / 默认 Python 命令入口”写成可执行规则；若用户尚未确认，则明确标成待确认，不要伪造确定答案
- @动作: 若本轮需要生成 `project-context.md`，则写清其与 `AGENTS.md` 的职责边界：前者解释项目，后者约束执行
- @动作: 在 `project-context.md` 中优先沉淀：项目一句话画像、当前阶段判断、关键层次结构、设计倾向、理解顺序、常见误判提醒、BMAD 上下文入口
- @动作: 文档中只写“后续 skill 稳定执行真正需要的事实”，不要堆项目介绍性内容

### @步骤8: 校验并交付

<!-- @类型: 操作步骤 -->
<!-- @优先级: 必须 -->
<!-- @依赖: step-generate-docs -->
<!-- @验证点: 初始化工件可被后续 skill 消费，且没有关键缺项 -->
<!-- @验证方式: 检查输出文件存在、结构完整、事实一致，并给出后续建议 -->
<!-- @ID: step-validate-handoff -->

- @动作: 复核输出文档与扫描事实是否一致，尤其是 Git 根、主代码仓库、BMAD 工件目录、测试入口
- @动作: 复核初始化文档的语言是否一致，术语是否稳定，例如 `project container` / `项目容器目录`、`primary code repo` / `主代码仓库`
- @动作: 复核 Python 环境相关表述是否符合用户确认结果；尤其检查 `.conda.env`、conda 环境名、Python 版本与执行命令是否被误写成未经确认的事实
- @动作: 复核 `AGENTS.md` 是否已经写入任务收尾说明，而不是只在初始化任务本次输出里出现一次
- @动作: 若生成了 `project-context.md`，复核其是否真的在解释项目，而不是重复执行规则
- @动作: 在交付说明中按需引用 `reading_priority`，直接指导后续 agent 先读什么、为什么先读
- @动作: 明确指出仍需用户确认的高风险事实，例如“主仓库到底是根目录还是子目录”“某个子模块是否独立收尾”
- @动作: 若仍存在高风险待确认事项，先暂停并向用户逐项确认；只有在用户明确接受“先产出草稿”时，才把这些事项写入文档的“待确认事项”
- @动作: 若用户后续补充确认结果，必须回填更新 `AGENTS.md` 或 `project-context.md`，不要只在对话里口头确认
- @动作: 收尾时必须按 [output-contract.md](references/output-contract.md) 给出结构化总结，至少说明：`本轮完成度`、`主线目标是否完成`、`已完成的关键改动`、`已执行的验证`、`未完成 / 阻塞项`、`下一刀建议`
- @动作: 如果本轮属于路线图、长任务或多阶段主线，还必须补充 `整体目标完成度` 与 `百分比口径`，并明确该百分比是在按“主线里程碑”“交付范围”还是“阶段拆分”估算
- @动作: 收尾表达顺序固定为“先回答主线目标是否完成，再回答验证证明到哪了，最后说明剩余问题属于哪种性质”；不要只给一句“任务已完成”
- @动作: 不要把可选优化、额外治理、无关验证缺口混进主线完成状态；未完成项应标明性质，例如“主线未完”“外部阻塞”“验证缺口”“后续治理”“可选优化”
- @动作: 给出下一步建议：如运行 `kz-bmad-run`、补生成 `project-context.md`、或继续细化 `AGENTS.md` 的项目约束
