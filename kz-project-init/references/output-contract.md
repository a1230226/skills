## 目的

这份参考文档规定 `kz-project-init` 默认要产出的初始化工件，以及每个工件应该承载什么信息。

## 输出语言

- 支持至少两种输出语言：`中文`、`English`
- 建议通过 `${OUTPUT_LANGUAGE}` 显式指定目标语言
- 如果用户未指定，默认跟随当前对话语言；无法判断时默认使用 `中文`
- 文件名与路径保持项目既有约定，语言切换只影响标题、正文、提示与待确认事项

## 默认产物

### 1. `AGENTS.md`

这是项目级 AI 协作规则主入口，也是默认唯一必产出的初始化文档，至少应包含：

- 输出语言说明
- 项目目标与范围
- 目录职责
- Git 根与默认工作目录规则
- Git 根路由与默认 `git -C` 执行位置
- 主分支推断、分支与收尾约定
- 多仓库暂停点与高风险确认点
- 统一本地命令入口
- 本地入口与门禁映射
- 运行 / 测试 / 格式化入口
- 并行开发热点与高风险目录
- BMAD 工件所在位置
- 哪些改动必须补 snapshot / fixture / schema / 文档
- 任务收尾说明：至少包含 `本轮完成度`、`主线目标是否完成`、`已完成的关键改动`、`已执行的验证`、`未完成 / 阻塞项`、`下一刀建议`

如果项目属于路线图、长任务或多阶段主线，`AGENTS.md` 还应明确：

- `整体目标完成度`
- `百分比口径`

## 可选产物

只有在用户明确要求时才追加：

- `project-context.md`
- 结构化 `repo-map.json`
- 特定技术栈的初始化补充文档

## 更新策略

默认不是“看到同名文件就整体重写”，而是按以下顺序判断：

1. 现有文档与扫描事实基本一致时，优先增量补齐缺失章节。
2. 现有文档结构可用但事实局部过时时，只重写冲突章节。
3. 只有当旧文档把错误 Git 根、错误主仓库或错误收尾规则固化为规范时，才整体重写目标文件。
4. 如果关键事实仍冲突，先在 `AGENTS.md` 中写结构化“待确认事项”，不要抢先把不确定内容写成硬规范。
5. 如果待确认事项会影响 Git 路由或主代码仓库判断，优先暂停向用户确认，而不是直接把问题留到文档里。

## 写作约束

1. 只写对后续 skill 真正有用的事实。
2. 未确认的事实单列为“待确认事项”，不要写成硬规范。
3. 多仓库项目必须在文档中明确区分“项目容器目录”和“实际代码仓库”。
4. Git 根、默认工作目录和主分支口径必须在 `AGENTS.md` 内保持一致。
5. 同一轮初始化默认输出单一语言，不在同一章节内中英混排；代码、命令、路径等技术字面量保持原样。
6. 初始化结果应优先暴露“规则入口、命令入口、门禁入口、证据入口”四类关键信号，帮助后续 skill 少猜测。
7. 即便项目拓扑复杂，也优先把目录职责、仓库归属和路由规则直接写进 `AGENTS.md`，不要默认再拆侧车文档。

- @动作: 不要把可选优化、额外治理、无关验证缺口混进主线完成状态里

- @动作: 如果验证尚未覆盖主线目标的全部关键路径，应明确写出“验证证明到哪了”，不要用笼统的“已验证”带过

- @动作: 如果任务属于路线图、长任务或多阶段主线，还必须说明：`整体目标完成度：Y%`
- @动作: 同时说明 `百分比口径`，明确该百分比是按主线里程碑、交付范围、阶段拆分还是其余约定估算
- @动作: 不要把本轮小收尾误写成整体主线已完成；整体目标状态与本轮完成度必须分开表达

## 推荐收尾模板

```text
1. 本轮完成度：X%
2. 主线目标是否完成：已完成 / 部分完成 / 未完成
3. 已完成的关键改动：
4. 已执行的验证：
5. 未完成 / 阻塞项：
6. 下一刀建议：
```

如果任务属于路线图、长任务或多阶段主线，还必须追加：

```text
7. 整体目标完成度：Y%
8. 百分比口径：
```

最小表达纪律：

1. 先回答主线是否完成，再回答周边是否完成。
2. 不要只写“任务已完成”。
3. 若主线未完成，要说明还差的是实现问题、外部依赖问题，还是验证证明不足。
